# Architecture Decisions

Short decision log. Each entry records what was chosen and why.

| # | Date | Decision | Rationale |
| --- | --- | --- | --- |
| AD-1 | 2026-11-08 | Host the SPA on **S3 + CloudFront** (private bucket, Origin Access Control). | Standard, low-cost hosting for `adapter-static` output, with HTTPS and SPA fallback routing. |
| AD-2 | 2026-11-08 | **Serverless REST API**: API Gateway HTTP API with a JWT authorizer, plus AWS Lambda. | Costs nothing when idle, scales automatically, little to operate. API Gateway rejects unauthenticated calls before any code runs. |
| AD-3 | 2026-11-08 | Store user data as **per-user JSON objects in S3** under a `users/{sub}/` prefix. | Simple and cheap for documents saved and loaded whole. The Lambda builds the prefix from the verified token's `sub` claim, never from client input. |
| AD-4 | 2026-11-08 | **AWS CDK in Python** for infrastructure; **Python** for the Lambda code. | Owner's preference. |
| AD-5 | 2026-11-08 | **Amazon Cognito User Pool** with managed login: Google and Facebook federation, plus native email accounts. **No account linking**: each sign-in method creates its own Cognito user. | AWS-native, low cost, and issues the JWTs that API Gateway validates. |
| AD-6 | 2026-11-09 | Keep each user's **project list as one JSON file in S3** (`users/{sub}/projects.json`) holding each project's ID, name and timestamps, not a list of files. Each project's **S3 folder is computed** from the user's `sub` and the project ID (`users/{sub}/projects/{id}/`). Only the API Lambda writes it, with conditional writes (`If-Match` on the ETag), retried on conflict. | Owner's preference: S3 is the only data store. The folder's contents are the source of truth for files, so the list changes only on create, rename and delete. Conditional writes stop two browser tabs overwriting each other. |
| AD-7 | 2026-11-09 | **Generate the SVG images from the uploaded PDF** in a separate processing Lambda, triggered by the S3 upload event. Processing status goes in a per-PDF `status.json` inside the project folder. | Rendering a PDF can take several seconds, so it runs in the background instead of holding an API call open. A status file per PDF has a single writer, so the processing Lambda never touches the project list. |
| AD-8 | 2026-11-09 | **The browser sends PDFs straight to S3** using a presigned POST issued by the API, limited to `application/pdf` and 20 MB, at the project's own S3 path. | Avoids API Gateway and Lambda payload limits. The presigned policy fixes the S3 key and size, so the browser can't write anywhere else. |
| AD-9 | 2026-11-08 | **The browser downloads images using short-lived presigned GET URLs** (about 5 minutes), issued by the API only to the project's owner. | Avoids passing image data through Lambda. |
| AD-10 | 2026-11-09 | The S3 upload event invokes the processing Lambda with **no automatic retries**, and an **on-failure destination** (an SQS queue plus a small failure-handler Lambda) writes `status: failed` if the processing Lambda crashes or times out. | A retry would start again from the beginning and break the 2-minute target, and without a failure handler a crashed run would leave the PDF stuck in `processing`. |
| AD-11 | 2026-11-09 | JSON data files are read and written **through the API** (with server-side size and schema checks), not with presigned URLs. The API rejects any JSON file larger than **1 MB** (HTTP 413). | The files are small (about 50 KB), and the API can validate them before saving. The 1 MB limit gives about 20 times headroom over normal files while stopping a faulty or malicious client from storing huge files. |
| AD-12 | 2026-11-09 | An **S3 lifecycle rule** on the data bucket permanently removes old (noncurrent) object versions **30 days** after they are replaced or deleted. | The bucket is versioned so lost or overwritten files can be recovered for 30 days. The rule stops deleted projects costing money after that. |
| AD-13 | 2026-11-09 | The web app keeps a **browser-side cache of generated SVGs** (Cache API or IndexedDB), keyed by user, project, file and page (`{sub}/{projectId}/{fileId}/{n}`). Before asking the API for a download URL, the app checks the cache and only downloads images it doesn't already have. Cached images **persist across sign-out and sign-in**, so a returning user doesn't download them again. The app only ever reads entries under the signed-in user's own `{sub}`. Entries for a project are removed when it is deleted, and the oldest entries are evicted if the browser's storage quota is reached. | Generated SVGs never change once made (a new upload gets a new `fileId`), so cached copies never go stale. Presigned URLs differ on every request, which defeats the browser's normal HTTP cache, so without this each project open re-downloads every image and pays S3 data-transfer charges (about $0.09/GB after the monthly free allowance). |
| AD-14 | 2026-11-17 | **dev, test and prod share a single AWS account** (`303770518256`) (NF-5). Each environment is a separate set of CDK stacks deployed from the same code, with the environment name in every stack and resource name (for example `takeoff-dev-data-303770518256`, since S3 bucket names must be unique across all AWS accounts). Each has its own S3 buckets, Cognito User Pool, API, Lambdas and CloudFront distribution. IAM roles and policies are scoped to their own environment's resources only. | Owner's preference: one account is simpler to set up and manage. Account-level separation isn't available, so isolation comes from separate resources and tightly scoped IAM, and all environments share the account's service quotas (for example Lambda concurrency). |
| AD-15 | 2026-11-17 (updated 2026-11-22) | **Every regional resource in every environment is deployed to `eu-west-2`** (NF-6). CDK is bootstrapped only there, stacks are pinned to that region, and nothing uses cross-region replication or copies data to another region. The one exception is the ACM certificates that CloudFront and Cognito custom domains must have in `us-east-1` (AD-22). They hold configuration only, and live in the account-wide `Takeoff-domain` stack (development plan, Stage 15), which `takeoff-admin` deploys without a CDK bootstrap in `us-east-1`. | NF-6 requires UK data residency, and `eu-west-2` is the only AWS region in the UK. AD-22 sets out what may be outside `eu-west-2`: access through edge locations and global services that hold only configuration, but no storage or compute. |
| AD-16 | 2026-11-17 | **Deployment access** (was DN-2): the owner is the **only deployer**, to every environment. They sign in as a single **IAM user** with a console password and **MFA**, and `aws login` gives the CLI short-lived credentials (no long-term access keys). **One IAM user (`takeoff-devops`) and one AWS CLI profile (`takeoff`, region `eu-west-2`) are used for all deploy, script and test actions** in dev, test and prod. Account-wide admin tasks use a separate identity (AD-17). CDK is bootstrapped once, so all environments share its deploy roles. The environment is chosen only by `-c env=…` (CDK), the `<env>` argument (scripts and `just` recipes, for example `just deploy dev`) and `--env` (pytest). | Owner's preference: with one person deploying, separate roles or profiles per environment add set-up without adding much protection. Nothing in IAM stops a command aimed at dev from changing prod; the protection is choosing the environment correctly, a typed confirmation before every prod deploy (`scripts/dev/deploy.py`; `infra/app.py` refuses prod without it), and the test suite's refusal to run integration tests against prod. |
| AD-17 | 2026-11-17 (updated 2026-11-22) | **Least-privilege deployment; no `AdministratorAccess` for `takeoff-devops` or `takeoff-admin`; only a separate administrator account creates users and assigns permission policies.** (1) **`takeoff-devops`** may only assume the CDK bootstrap roles (`cdk-hnb659fds-*`) and use a scoped policy for scripts and tests, limited to `takeoff-*`/`Takeoff-*` resources in `303770518256`/`eu-west-2`; a final statement denies every action requested in another region, apart from a named list of global actions (IAM reads and the policy simulator, CloudFront invalidation, STS, and the sign-in actions `aws login` uses). (2) CDK is bootstrapped with a **custom CloudFormation execution policy** (`Takeoff-cf-exec`) instead of `AdministratorAccess`: only the services the stacks use, regional actions only in `eu-west-2` (apart from the global services allowed by AD-22), and IAM limited to roles named `Takeoff-*` that carry the **permissions boundary** `Takeoff-boundary`. Changing or removing any permissions boundary, or editing the `Takeoff-*` access policies, is denied. (3) The CDK app sets `@aws-cdk/core:permissionsBoundary` so every role it creates gets `Takeoff-boundary`, which limits Lambda and custom-resource roles to the same services. (4) **The administrator** is a separate IAM user with special rights. It is managed outside this project, which simply assumes it exists. It does every task that creates or manages an IAM user or assigns a permission policy to a user or role: creating `takeoff-admin` and `takeoff-devops` (including their console passwords and MFA), creating and changing `TakeoffAppPlatform`, attaching policies to both users, and running **`cdk bootstrap`** (which creates the `cdk-hnb659fds-*` roles and attaches `Takeoff-cf-exec` and their other policies to them). (5) **`takeoff-admin`** (MFA, CLI profile `takeoff-admin`) only deploys the **`Takeoff-access`** stack and, from Stage 15 of the development plan, the **`Takeoff-domain`** stack (hosted zones, `CAA` records and the `us-east-1` certificates, AD-15), using its own credentials (no bootstrap needed). That stack holds only **unattached** customer managed policies (`Takeoff-cf-exec`, `Takeoff-boundary`, `Takeoff-devops-cdk`, `Takeoff-devops-scripts`) and no users. `takeoff-admin` has `SignInLocalDevelopmentAccess` (for `aws login`) and the customer managed policy **`TakeoffAppPlatform`** (`infra/policies/TakeoffAppPlatform.json` in `take-off-backend`), which allows only the `Takeoff-access` stack and creating, reading, versioning, tagging and deleting `Takeoff-*` managed policies (from Stage 15 also the `Takeoff-domain` stack, ACM certificates in `us-east-1`, and creating hosted zones and changing their records, but not deleting zones or registering domains). It has **no permission to create or manage any IAM user or role, or to attach, detach, put or delete a policy on any user, role or group**. `TakeoffAppPlatform`'s name is outside `Takeoff-*`, so `takeoff-admin` can't edit its own policy. (6) The policy **names** in `Takeoff-access` are fixed. A change to a policy's contents takes effect wherever the administrator attached it, but a new or renamed policy needs the administrator to attach it (and CloudFormation can't delete a policy that is still attached). | Owner's requirement: neither `takeoff-devops` nor `takeoff-admin` may have admin rights, and identities and their permissions are granted only by an administrator outside the project. With the default bootstrap, any CDK app could create an admin role through the execution role, so restricting only the user would hide admin rights rather than remove them. The boundary stops a deploy from creating a role more powerful than the boundary. Without user management or policy attachment, `takeoff-admin` can't give itself more rights or set any user's credentials. It still writes the policies that define what `takeoff-devops` and CloudFormation may do, so it must be guarded with MFA and used only for that task, and the administrator must never attach a `Takeoff-*` policy to `takeoff-admin`. Cost: creating users, assigning policies, adding a new `Takeoff-*` policy, bootstrapping or upgrading the bootstrap, and changing `TakeoffAppPlatform` all wait for the administrator. A stage that uses an AWS service for the first time first needs `Takeoff-cf-exec` and `Takeoff-boundary` (and, if a script needs it, `Takeoff-devops-scripts`) updated by `takeoff-admin`. |
| AD-18 | 2026-11-17 | **uv manages Python and dependencies.** `pyproject.toml` lists dependencies (dev tools in a `dev` group), `uv.lock` pins every package version, and `.python-version` pins **Python 3.13** (the Lambda runtime, P-4). Commands run through `uv run` (for example `uv run pytest`, `uv run python scripts/dev/deploy.py …`), and `cdk.json` runs the CDK app with `uv run`. Lambda dependencies are exported from the lock file with `uv export` into a `requirements.txt` when a Lambda is packaged. | Owner's choice. The lock file makes installs repeatable on any machine and over time; uv also installs the pinned Python version, and `uv run` avoids activating a virtual environment (which PowerShell's execution policy can block). |
| AD-19 | 2026-11-17 | **The CDK CLI is pinned in the repo.** A root `package.json` lists `aws-cdk` at an exact version as a dev dependency, `package-lock.json` is committed, `npm ci` installs it, and every CDK command runs as `npx cdk …` (including in `scripts/dev/deploy.py`). Upgrade `aws-cdk` (npm) and `aws-cdk-lib` (uv) together. | Owner's choice. The CLI is versioned separately from `aws-cdk-lib`, and a CLI older than the library fails to synth or deploy. Pinning both in the repo makes every machine use the same versions and makes upgrades one deliberate change. |
| AD-20 | 2026-11-17 (updated 2026-11-21) | **just is the project's command runner.** A `justfile` at the repo root has a recipe for every routine command: setup, lint, test, synth, the pre-deploy `check`, deploys, bootstrap, sign-in, integration tests and each script in `scripts/`. Recipes run in `sh` in WSL (AD-21); the `justfile` also sets PowerShell as its Windows shell, so recipes still run natively on Windows as a fallback. Recipes are thin wrappers; safety checks (prod confirmation, account check) stay in the Python scripts, so they apply however a script is started. | Owner's choice. One short, listed set of commands (`just` shows them) instead of long `uv run …`/`npx cdk …` lines, the same on every machine. |
| AD-21 | 2026-11-21 | **WSL with Debian 13 ("trixie") or later is the default development environment for `take-off-backend`.** The repository is cloned into the WSL Linux filesystem (for example `~/dev/take-off-backend`, with `theserver` beside it), and just, uv, Node.js, the AWS CLI and Poppler (`poppler-utils`) are installed there. The AWS CLI profiles (`takeoff`, `takeoff-admin`) are configured and signed in inside WSL. Native Windows stays possible as a fallback: the code keeps its Windows handling (`npx.cmd`, the `justfile`'s PowerShell shell). Line endings are fixed to LF by `.gitattributes`. | The Lambdas run on Linux (P-4), and the processing Lambda calls Poppler, which installs natively on Linux but only through third-party builds on Windows. Developing on Linux means local tests and the Stage 9 rendering measurements use the same kind of OS and tools as Lambda, with no Windows-only code paths. Keeping the clone on the Linux filesystem avoids the slow file access of `/mnt/<drive>`. Debian 13 is the first Debian release that packages `just`; Debian 12 and earlier don't, even in backports. |
| AD-22 | 2026-11-22 | **UK residency means storage and compute in `eu-west-2`; access through AWS edge locations is allowed** (resolves DN-1 and DN-20; NF-6). Every resource that stores data or runs code (S3 buckets, the Cognito User Pool, Lambdas, queues, log groups, SES) is in `eu-west-2`. Users may reach the service through AWS edge locations outside the UK: CloudFront serves and caches the public SPA files, and the Cognito custom sign-in domain (Stage 15) runs through CloudFront, so sign-in traffic passes through edge locations over TLS. Edge access is allowed, not required. Global services that hold only configuration are allowed: IAM, Route 53, AWS Budgets, CloudFront distribution settings, and ACM certificates in `us-east-1` for CloudFront and Cognito. Nothing runs at the edge: **no CloudFront Functions and no Lambda@Edge**. | Owner's requirement: keep data storage in the UK and keep the design simple. Edge access gives fast, cheap HTTPS hosting without a UK-only alternative (API Gateway or a load balancer in front of S3), and TLS protects data in transit. Banning edge code keeps all compute in `eu-west-2`, and keeps Stage 15 simple (no `www` or default-domain redirects, no API custom domain). |
| AD-23 | 2026-11-22 | **Zip-packaged Lambdas are bundled locally with uv, without Docker.** Their third-party packages are a `lambda` dependency group in `pyproject.toml`, pinned in `uv.lock`. At synth time a CDK local bundling step exports that group and runs `uv pip install --target … --python-platform aarch64-manylinux_2_28 --python-version 3.13 --only-binary :all:`, then copies `lambdas/` alongside. boto3 is not bundled (the runtime provides it). Container-image Lambdas (the processing Lambda) are built separately. | Needs no Docker and no new permissions; the unit tests and the deployed Lambda use the same locked versions; covers every package planned so far, including ones with compiled code that publish Linux arm64 wheels. Rejected: Docker bundling with `aws-lambda-python-alpha` (Docker on every synth, slow arm64 emulation on x86, alpha API, a separate requirements file) and the public Powertools layer (covers only Powertools, a second version source, a cross-account `lambda:GetLayerVersion` permission). |
| AD-24 | 2026-11-22 | **API throttling of 2 requests per second steady and 10 burst** on each environment's HTTP API stage (resolves DN-9). To be reviewed in Stage 13, before prod opens to users. | Keeps cost and abuse low while the API is unauthenticated (Stage 1 to Stage 5) and during development. Below the expected prod peak (about 4 saves per second, plus polling and image requests), so prod will probably need higher limits. Integration tests must stay within the burst and retry on 429. |
| AD-25 | 2026-11-24 | **Project and file IDs are ULIDs** (resolves DN-5): 26-character, upper-case Crockford base32 strings, generated by the server with the `python-ulid` package (`lambdas/common/ids.py`). Every S3 key builder rejects an ID that is not a valid ULID. | ULIDs sort by creation time, which helps when listing, and are safe in S3 keys and URLs. A small, maintained library avoids hand-written ID code. |

## Proposed (not yet confirmed)

| # | Proposal | Rationale |
| --- | --- | --- |
| P-2 | **PDF-to-SVG library shortlist**: (1) **Poppler `pdftocairo -svg`** (GPL), run as a separate program in a Lambda container image: the leading free option; (2) **Apache PDFBox + Apache Batik** (Apache 2.0) in a Java Lambda with SnapStart: the safest licence, but slower and less faithful on complex PDFs; (3) **hayro-svg** (MIT/Apache 2.0) in a Rust Lambda: fast and permissive, but young and unproven. **Fallback** if none have high enough quality: a commercial licence (MuPDF/PyMuPDF from Artifex, or Aspose.PDF). |
| P-4 | **Lambda settings**, all on **arm64 (Graviton)**: **processing Lambda** starts at **2 GB** of memory with a **3-minute timeout**; **API Lambda** at **512 MB**; **failure-handler Lambda** at **256 MB**. Image generation has a **2-minute budget** (NF-4): the processing Lambda checks the elapsed time after each page and, if the budget runs out, stops and writes `status: failed`. The processing Lambda **renders pages one at a time** in a single process, which keeps memory use bounded and the code simple. Final memory sizes are set by running **AWS Lambda Power Tuning** with real PDFs. | Lambda charges memory × run time, and CPU grows with memory (about one vCPU at 1,769 MB). Single-threaded Python rendering gains little above about 2 GB, so that is the starting point. arm64 is about 20% cheaper than x86. The API Lambda mostly waits on S3, so 512 MB gives fast cold starts at low cost. The extra minute of timeout lets the processing Lambda record a failure cleanly instead of being cut off. |
